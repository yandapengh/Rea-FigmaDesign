圖譜是什麼：一張可以被問問題的結構圖

不是視覺化的網，也不是 AI 的腦。它是一棵樹，加上一張「身分證」規則——讓「哪些頁面一樣、哪些是彈窗」變成可以算的問題。

實作篇：一次真實的查詢 · 方法篇：數據脫水的核心方法

00一張圖，先回答三個問題

對非技術讀者，圖譜只需要回答三件事：

問題答案的一句話
為什麼要長成這樣？因為設計稿本身就是「誰包含誰、誰蓋在誰上面」的樹
為什麼 agent 拿到的資料是準的？它拿的是算好的欄位，不是自己看圖；每個答案都掛著可查的 ID
為什麼不是掃一遍全量？判斷只看每個畫面的頂層結構（全檔 2.3% 的節點），其餘靠預先算好的索引

01一個畫面的骨架

這是 1:102753（一個真實的彈窗）在圖譜裡的樣子。每個方塊是一個節點；線是「包含」關係；z 是誰蓋在誰上面。

從這張圖可以直接讀出三件事，也就是圖譜的三個元素：

元素在這張圖上可以回答什麼
邊誰連到誰（parent_id）這頁包含哪些區塊
順序z：0 → 1 → 2誰蓋在誰上面（彈窗的關鍵）
尺寸390×844 vs 280×276誰是遮罩、誰是面板

02同一種，怎麼算

人看得懂「這兩個彈窗長一樣」，程式不行。所以每個節點先算一張身分證：

hash(節點) = md5( 型別 + 依序的子節點 hash )

算法是由下往上：先算子節點，再把子節點的號碼依序串起來，算父節點。所以整棵子樹的形狀，最後會變成一個短碼。

03規則疊在圖上

有了圖與身分證，彈窗就可以寫成三個條件，而且每個條件都對應圖上的一個位置：

條件在圖 1 的哪裡
這一層與畫布同尺寸（±3px）mask 的 390×844
這一層的子樹沒有文字mask 子樹 0 個 TEXT（面板的 7 個不算）
緊鄰上方是更小的面板z2 的 Dialog-Slot 280×276

三個都成立 → overlay-panel。所以「判斷彈窗」在圖譜上不是找相似圖片，是對每個畫面的頂層子節點做一次條件檢查。

這就是為什麼 agent 拿到的答案是準的：它拿到的是「這個檢查已經跑完的結果」——archetype 這個欄位——而不是需要它自己看圖推論的東西。

04不是掃全量

「不掃全量」不是修辭，是可以量的。這份檔案有 163,601 個節點，判斷實際只碰了 3,831 個（2.3%）：

為什麼可以只看頂層？因為彈窗的定義是「畫布上蓋了一層遮罩」，這件事發生在畫面的頂層，不會藏在第 20 層的子節點裡。

05為什麼這樣是準的

三個理由，都不依賴模型：

理由證據
規則被人工標註驗證過42 個標註：precision / recall 1.00
實地抽查過10 個節點，設計師在 Figma 逐一比對：10/10
答案可回查每個結果都帶 node id；說錯可以重跑

Agent 的工作只是把「已算好的欄位」翻譯成句子；它不需要相信自己的眼睛，也不需要相信模型的印象。

06邊界

情況會怎樣
遮罩被畫進元件內部、沒有獨立圖層可能判成 page，需要人工複審
全螢幕但沒有遮罩（引導頁）落在 page，這是對的
畫布尺寸不同（不是 390×844）要改掃描尺寸參數，否則掃不到

所以答案永遠帶著定義：「結構上的彈窗有 87 個」。
