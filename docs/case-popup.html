一次真實的查詢：哪些頁面是彈窗

從一句話，到一個可以貼回 Figma 的答案。中間發生了什麼、用了哪個工具、為什麼那些數字能代表彈窗。

這是「數據脫水的核心方法」的實作篇：方法講資料形狀，這裡講一次完整的執行。

00任務

「這份檔案裡，哪些頁面是彈窗？大概有多少個？」

這句話裡有三個模糊的地方：

  • 「彈窗」——是視覺上有遮罩層，還是設計師分類為 dialog？
  • 「哪些」——要清單還是只要數量？
  • 「這份檔案」——資料在哪裡、用哪個版本？

Agent 不會一開始就知道答案。它先要知道自己有什麼工具，再決定怎麼問資料。

01agent 的起點：工具清單與操作規範

Agent 啟動時看到兩樣東西，沒有第三樣：

1. 工具清單（MCP 提供）

每個工具的名稱、描述、參數 schema。例如：

list_screens
  Enumerate screens with their layout archetype and count them
  by archetype. Default unique:true keeps one row per (structure
  hash + headline), so 512 duplicated screens collapse to 291.

描述裡已經寫清楚：這是「列舉 + 計數」，預設去重，去重的鍵是結構 hash 加標題。

2. 操作規範（docs/SKILL.md）

專案自己的規則，補上工具描述不會講的事：

| 這份檔案有哪些畫面？各類型有幾個？ | list_screens |
| 這一頁長什麼樣？                   | screen_sheet |

「有多少」一律先 list_screens，不要自己遍歷資料庫。
Agent 不是讀了一份神秘的「工具呼叫 skill」。它的起點是公開的工具描述加上專案的操作規範，兩者都可以被人檢查與修改。

02選工具：列舉，而不是單體

任務問的是「哪些、多少」——這是列舉問題，不是「這一頁長什麼樣」。

任務語意
哪些 / 多少
→
讀工具描述 + SKILL
→
選 list_screens
列舉 + 計數
→
不要先猜 ID

圖 1：工具的選擇來自任務形狀，不是關鍵字。

如果選錯工具會怎樣？

選錯後果
screen_sheet它一次只回一頁，要先知道 ID。拿它回答「有多少」只能靠猜
直接查資料庫Agent 得自己寫 SQL、自己判斷版面原型——把計算搬進模型，結果不可重跑

選 list_screens 的理由很單純：它一次回全部，而且數字是 server 算的。

03呼叫與回傳

實際呼叫（{} 代表不帶參數、取預設去重）：

tools/call  list_screens  {}

回傳（省略 291 筆明細，只留統計）：

total  291
page   172
overlay-panel  87
overlay        32

其中一筆明細長這樣：

{ "id": "1:102753", "name": "Dialog-page", "page": "Withdraw",
  "archetype": "overlay-panel", "nodes": 51,
  "family": "d4319d6dc784" }

三個數字放在一起，答案的形狀就出來了：

87 個有面板的彈窗 · 32 個只有遮罩、沒有面板 · 合計 119

291 是「不同畫面」的數量（結構 + 標題去重），不是節點數，也不是畫面總數（原始 512 張含複本）。

04為什麼 1:102753 是彈窗

這不是模型「看圖」判斷的，是三個條件在資料上都成立。

先看它在資料庫裡的三個直接子節點：

child_index型別名稱尺寸子樹文字節點
0SLOTpage-slot390 × 8440
1INSTANCEmask390 × 8440
2SLOTDialog-Slot280 × 2767

注意看最後一欄：面板裡有 7 個文字節點，遮罩層是 0。彈窗當然有文字——文字在面板那一層，不在遮罩層。判斷的是遮罩沒有文字，不是整個彈窗沒有文字。

條件一
這一層與畫布同尺寸mask：390 × 844，容差 ±3px
條件二
這一層的子樹沒有文字mask 子樹 0 個 TEXT；面板有 7 個，但不算在內
條件三
緊鄰上方是更小的面板child_index 2 的 Dialog-Slot，280 × 276，面積小於畫布一半
三個條件同時成立 → overlay-panel

換一個對照：1:102743（Withdraw 頁）的子節點是狀態列 390×47、導覽列 390×44、內容 390×492、Home indicator 390×34、Toast 96×96。沒有任何一個是 390×844——所以它是 page。

判斷用的是 bbox + child_index + 這一層子樹有沒有文字。這三個欄位在第一次抽取時就寫進 SQLite，之後每次查詢都不必再開 Figma。

為什麼要檢查文字？如果一個「整頁大小的圖層」上面浮著小元件（例如 Toast），沒有文字檢查就會被誤判成彈窗。遮罩是純色／半透明矩形，不該有文字；有文字的整頁圖層是內容，不是遮罩。

05為什麼離散的資料能判斷「相似」

因為「相似」不是比圖片，是比結構。

每個節點都有一個結構 hash

hash(節點) = md5( 型別 + 依序的子節點 hash )

子樹被壓成 32 字元。相同結構 → 相同 hash → 同一個家族。

回到 1:102753，它的 hash 是 d4319d6dc784。問「這頁有幾個複本」：

screen_family  1:102753
→ hash d4319d6dc784
→ members: 1:103166, 1:102908, 1:102765, 1:102761 …
   每個都是 51 個節點，Dialog-page

這就是「特徵相似」在離散資料上的樣子：不是像素接近，是同一組結構關係。同一個彈窗被複製了 20 次，在資料裡就是同一個 hash 出現 20 次。

那規則本身怎麼來的？

三條件不是憑空發明，是從設計師的工作方式反推的：

設計師怎麼做資料上長怎樣
彈窗會蓋住整個畫面遮罩與畫布同尺寸
遮罩本身沒有內容遮罩子樹沒有文字
面板浮在遮罩上面child_index 更大、尺寸更小

三個條件在 42 個人工標註上 precision / recall 都是 1.00，10 個節點實地抽查 10/10 一致。

06邊界：什麼時候會不準

情況會怎樣
遮罩被畫進元件內部，沒有獨立圖層可能判成 page，需要人工複審
全螢幕但沒有遮罩的頁面（例如引導頁）會落在 page，這是對的
畫布尺寸不是 390×844需要改掃描的尺寸參數，否則一頁都掃不到

所以答案要附定義與 ID：「結構上的彈窗有 87 個」，而不是「彈窗有 87 個」。

07回到任務

完整的回答：

這份檔案有 291 個不同畫面。結構上的彈窗有 119 個：87 個帶面板、32 個只有遮罩。
如果你指的是「設計師分類為 dialog」，目前只有 42 個畫面有標註，其餘無法判定。
例：1:102753 是帶面板的彈窗（51 個節點，家族 d4319d6dc784）。

要清單就再往下鑽（list_screens 帶 archetype）；要確認就開複審看板，設計師勾選後把判斷寫回 labels。

整個流程裡，模型只做了三件事：讀懂任務、選對工具、把數字翻譯成答案。計數、分群、判斷，全部在資料層完成。
